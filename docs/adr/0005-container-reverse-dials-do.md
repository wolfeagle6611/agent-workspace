# ADR 0005: 容器反向拨号到 Durable Object

Status: accepted（外部系统既成决策，本文为逆向整理）

## 背景与决策

`computerd` 自己在容器里监听 `:8080`，DO 本可以直接连它。但作者让 DO 当 WebSocket 服务端：DO 准备一个升级槽，容器执行 `POST /connect`，从容器内拨出，经出网拦截器绕回 DO，WebSocket 在 DO 侧被接受。

两个原因。

第一，出网必须先布线。容器出网走 `container.interceptOutboundHttp`，由 DO 的 `Fetcher` 接管。让容器的连接走这条线，流量从一开始就在 DO 控制的路径上，不需要额外的信任假设。

第二，只有被服务端接受的 WebSocket 才能用 `ctx.acceptWebSocket()`。这扇门决定了 DO 以后能不能休眠。方向一旦反过来，休眠就永远做不到。

## 放弃的方案

**DO 主动连容器。** 延迟更低，少一跳。放弃原因：DO 到容器的入站路径要另外授权；而且这么做等于关掉休眠的可能。

**平台负责连接。** 放弃原因：连接生命周期就不再由 Workspace 掌控，水位对不上“操作对象”。

## 后果

- 每次重连都是全新会话。WebSocket 一断，Workspace 丢掉旧 Handle，下次 `ready()` 重新走启动三连：启动 → `/health` 轮询 → `/connect` 握手。
- DO 与容器是 1:1。这条关系是承重的：容器只有一个对端，水位只对一个对手方说话，休眠才有解。
- 启动顺序固定：先启动容器，再拦出网，再探健康，最后开 WebSocket。

## 对本项目的影响

若 Go 版的执行体是本地进程或同一主机上的容器，这条可以反转，代价是要自己解决“谁授权谁”。若执行体在远端，保留反向拨号能省掉一套入站授权。
