# ADR 0009: 写者分三类，工具写者可带 `baseRev`

Status: accepted（本项目决策）

## 背景

ADR 0007 把写者分成两类：能声明版本、版本不符就被拒绝的 API 写者，与不能声明版本的 exec。第三阶段出现第一个真实调用方（pi 经 MCP）。它既能读版本，也能写版本，所以它不落在 ADR 0007 的任何一类里。

## 决策

写者分三类。

| 类 | 成员 | `baseRev` |
| --- | --- | --- |
| API 写者 | `fs.WriteFile` / `Remove` / `Rename` / `Mkdir` / `Truncate` | 可选，带上即保护 |
| 工具写者 | MCP 的 `write` / `edit` | 可选；`read` 在结果里返回 `rev` |
| 不可中断写者 | FUSE、exec、pull | 不带，总是生效 |

工具写者属于第一类的第一个真实实例。不传 `rev` 时退回 last-write-wins，所以工具契约不是强制的。

## 放弃的方案

**工具强制带 `rev`。** 放弃原因：模型每次写都要先读，漏传就失败。对小改动这是纯摩擦，而摩擦会让人关掉保护。

**工具不带 `rev`。** 放弃原因：`baseRev` 就永远没有调用方。ADR 0006 说它必须在第一阶段做完，一个没人用的机制不算做完。

**exec 也带 `rev`。** 放弃原因：子进程无法表达前置条件，事后报冲突只会变成噪音（ADR 0007 已排除）。

## 后果

- 工具冲突必须回结构化的 `CurrentRev`，模型才能重读重试。只回一句话不够。
- exec 与 FUSE 仍可无条件覆盖工具写入。工具带版本不改变这条，ADR 0007 的三条用户约束照旧。
- 单写者约束仍是默认（每工作区 1 个并发执行）。`baseRev` 是额外保护，不是替代。
- 每加一个工具都要决定它属于哪一类。默认归工具写者。

## 重新评估的触发条件

1. 模型频繁漏传 `rev`，覆盖变成常态：回来讨论是否强制。
2. 多个 agent 共享一个工作区：回来讨论更强的一致性，`baseRev` 不够。
