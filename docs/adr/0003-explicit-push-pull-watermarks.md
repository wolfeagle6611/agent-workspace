# ADR 0003: 显式 push/pull + 水位线，不做透明同步

Status: accepted（外部系统既成决策，本文为逆向整理）

## 背景与决策

两份状态要一致，有两种做法：让挂载层透明同步，或在明确定义的时刻同步。

选第二种。DO 侧每次变更铸造一个单调 `rev`。同步只传对端 `rev` 水位之后的条目。水位存在 `_vfs_watermark` / `_vfs_fetch_cursor` 表里，与它描述的数据同一事务写入，所以不会漂。

命令执行用固定的包夹：push → spawn → 事件与结果 → pull。push 是安全门，不是优化：push 失败就不 spawn，避免命令看到过期视图。FUSE 打开时容器内的写入照常即时可见；回流的时机仍然是 pull。

## 放弃的方案

**透明同步。** 每次读写都触发同步。放弃原因：延迟不可控，一次 `stat` 可能触发网络往返；且难以定义“一致”的边界。

**整树快照。** 简单，但每次执行要搬全树。放弃原因：与状态大小成正比，agent 工作区很快超过可接受量。

**rename 操作码。** 目录改名能在线上压成一行。放弃原因：协议其余部分是状态式（live entries + tombstones），一个操作式条目会破坏幂等重放与冷启动重放。代价是目录改名按子树规模计费。

## 后果

- 冲突策略退化为 last-write-wins。文档明确指出：多个写者改同一文件会静默丢一方；读-改-写跨容器会丢失增量。
- 推荐用法写死为三条：同时只有一个活跃写者；按子树分区；把工作区当草稿而不是共享可变状态。
- 崩溃可续传。fetch 游标是 `(rev, path)`，不是标量，所以一次大改名的中断只重放 256 条，不重放整个 rev。
- DO 与 `computerd` 必须成对发布，协议没有版本协商。

## 对本项目的影响

这是最值得照搬的一条，也是最贵的一条。Go 版要复制的是“水位与数据同事务”这个约束，不是那几张表的具体形状。
