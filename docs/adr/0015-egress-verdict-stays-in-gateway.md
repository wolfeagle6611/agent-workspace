# ADR 0015: 出口网关不提供调用方自定义判定

Status: accepted（本项目决策）

## 背景

上游 `cloudflare/computer` 的出口策略是三值枚举，其中 `http-gateway` 把出网交给一个调用方提供的 `Fetcher`（`packages/computer/src/runtime/egress.ts:7`、`hostEgressFetch` `:26-36`）。判定代码写在调用方里，平台一行不管 —— 上游没有按 host 的允许/拒绝规则，也没有凭据注入。

我们的 `sandbox-gateway` 形状相反：它是宿主上的独立进程，自己判策略、自己换密钥、自己有错误码。对齐时的问题是：要不要也开一个「把判定权交给 harness」的口子。

## 决策

**判定权留在网关内。不提供 `Fetcher` 式策略插件，不接受调用方提交的判定代码。**

三条理由：

1. ADR 0010 的强制点论证要求「沙箱 root 清掉 guest 内规则后仍然无法直连公网」。把判定交给调用方，等于把边界交给调用方 —— 边界可以被下层关掉，就不再是边界。
2. 策略必须可审阅。spec 用户故事 28 要的是「用一个配置文件描述黑名单、绑定与出口路由」。判定代码散在 harness 里，审阅面消失。
3. 每条请求多一次跨进程判定调用，且判定结果无法在网关日志里完整复现。排障会从「读一行日志」退化成「追两个进程」。

**代价写在明面上**：新增策略必须改网关配置并重启（网关没有热载），不能由 harness 按租户临时下发。

## Considered Options

- **采纳上游的 `Fetcher` 模型**。收益：harness 可按租户提供策略，改动不用碰网关。代价：上面三条全中。否决。
- **折中：允许调用方提供「允许列表数据」但不提供代码**。收益：保住审阅面。代价：仍然是运行期策略数据，与「策略只重启生效」冲突，且这条能力没有提出需求。暂不做，需要时另开 ADR。
- **维持现状（判定在网关内，策略来自配置文件）**。采纳。

## Consequences

- `policy = blocked` 这类开关只能随沙箱注册落盘，不能运行期切换。
- harness 想改策略，必须走「改配置 + 重启网关」，或者「换沙箱」。
- 对齐文档 `docs/architecture/egress-gateway-alignment.md` 第 4 项记 `not-following`。
