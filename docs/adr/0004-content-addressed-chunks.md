# ADR 0004: 内容寻址分块 + manifest

Status: accepted（外部系统既成决策，本文为逆向整理）

## 背景与决策

文件要跨两条线传输，而 agent 工作区的常见形态是“大文件局部改、小文件大量生成”。

决策：按固定 512 KiB 切片，每片用 `sha256` 寻址。文件内容表示为 chunk 哈希序列，可选的 manifest 记录整个序列的哈希，让接收方一次判断“我是否已有这段文件”。

线上只传元数据与哈希，不内联字节。传字节前先探测：发送方调 `hasObjects`，只补对方缺的那部分。

## 放弃的方案

**整文件 blob。** 改一个字节就重传整个文件。放弃原因：日志、数据库文件、带 vendor 依赖的仓库都受不了。

**内容定义分块（CDC）。** 插入一个字节只影响局部分块。放弃原因：作者列为 future consideration，未采用。固定分块实现简单、寻址可预测，代价是插入式编辑会移动后续所有分块。

**在线压缩打包。** 放弃原因：多一层状态，收益与重复内容去重重叠。

## 后果

- 去重天然存在：同一份依赖铺在两个路径只存一份。
- 写入路径要为每个 chunk 算哈希，这是大顺序 IO 慢 30 倍的主因（见 docs/19）。
- 需要垃圾回收。`gc()` 清掉无引用且超过安全窗口的 blob 与 manifest。作者刻意不把它放到公开 API 上。
- 硬链接在同步中退化为“多个独立文件，内容相同”，inode 身份不过线。

## 对本项目的影响

Go 版直接用 `sha256` 与固定分块即可。真正需要照搬的是“先探测再传字节”的顺序，它把网络往返从 N 次压到 2 次。
