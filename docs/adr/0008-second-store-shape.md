# ADR 0008: 第二存储的形状

Status: accepted（本项目决策）

## 背景

ADR 0006 把水位、合并、探测补字节推到第二阶段，触发条件是“出现第二个存储”。现在按 go-mapping §5 第 6a / 6b 步落地，必须先定下对手方的形状，否则协议没有落点。

取法对象里，容器是唯一对端，反向拨号、休眠、出网拦截都与它的平台绑定。我们的部署没有这些约束，所以不能照抄它的连接形状。

## 决策

**对端是一个独立进程，用同一个二进制。** `agent-design serve --db <path> --socket <path>` 起来，独立库文件，独立挂载点，可被 `kill -9`。docker 容器只是同一条 socket 协议外面的包装，换过去只改启动器，不改协议。启动器与 `Transport` 之间是接口边界。

**正向拨号，走 unix socket。** 宿主连对端的 socket。宿主不开监听口，不用令牌。取法对象反向拨号的两条理由（出网布线、休眠）在 Go 侧都不成立。远端执行体出现时，反向拨号以 `Transport` 的另一个实现回来（ADR 0005 的“改造”结论）。

**镜像库耐久。** 镜像库放宿主可见的卷，容器重启读回同一个库。两侧用同一个 `internal/vfs`，schema 相同。镜像库不删即续传；删掉镜像库就是“空白对端”，走 `senderRev = 0` 全量路径。

**水位两侧都落库，一张表。** 宿主存 `push_rev` 与 `fetch_rev` / `fetch_path`；镜像存 `generation` 与 `applied_rev` / `applied_path`。表里字段一组，两侧各用各的。

**`generation` 取代 `ESYNC_LOST`。** 镜像库首建时写入随机 `generation`，握手时比对。一致即续传；不一致即复位两侧游标、全量重发。权威侧存着全部数据，所以“丢失”不可表示，只有“重发”。§7 的 `ESYNC_LOST` 与 `RuntimeIDs` 字段随之删除。

**线上编码是长度前缀帧加 JSON。** 一条消息一帧，对象流用同类帧加终止帧。chunk 字节走原始分段，不做 base64。

**墓碑与合并。** 变更日志 `vfs_changes(rev, path, kind, mode, mtime)` 追加写。合并按 `(rev, path)` 分页读，页长 256。同一路径可能跨页重发；这是允许的，因为应用是状态式而不是操作式。墓碑的保留条件是 `rev` 小于两侧水位；两侧都过了就删。

**pull 是第三个不受 `baseRev` 约束的写者。** 每批一个事务，一次铸一个 `rev`，按 last-write-wins 覆盖。落地为 §6 的一行：FUSE、exec、pull 三者都不带 `baseRev`。

**重连先 pull 再 push。** 镜像里可能有上次命令写完、还没回流的变更。先 push 会用宿主旧版本盖掉它们。

## 放弃的方案

**6a 用内联字节。** 放弃原因：那是另一种线形状，会把批大小、半批、续传这些真正要验的点推到 6b 才暴露。

**6a 用假存储的假对端。** 放弃原因：ADR 0006 反对的正是这个。假对端必须复用真 `vfs` 与真编解码，只在命名点关掉传输。

**保留 `ESYNC_LOST`。** 放弃原因：留一个永不抛出的码，调用方会写永远走不到的分支。

**镜像库临时化。** 放弃原因：那样“杀掉对端后重连，续传不重复应用”这条验收无法验证，只能验证全量重传。

## 后果

- 两侧共用一套 schema、一套 chunk 实现、一套 GC。多一个耐久库，少一套代码。
- 目录创建不产生变更事件（§6 既有约定）。因此空目录不传播，父目录随子项出现。要改先回来改这一条。
- `Handle` 缓存放 `Runtime`，按 backend id 单飞，`Closed()` 关闭即丢。§6 的“每次 Exec 一次 Connect / Close”作废。
- `runtime.Result` 加 `Sync`（`Complete` / `Pending`），因为 pull 失败不改写命令结果。
- GC 两侧共用，规则为“无引用且 `last_seen` 早于 60 秒”，触发点是 `Close` 与 blob 数量阈值。GC 不铸 `rev`。

## 落地顺序

**6a：协议。** 变更日志、水位、合并分页、应用、探测补字节、帧编解码（`internal/peer`）、`net.Pipe` 假对端与五个断点。验收：断点矩阵全绿。

落地后的两条实现事实：

- 发送方在本地合并自己的日志，`changes` 请求只用于 pull 方向。跨链路只有条目、哈希与缺失字节。
- 帧上限 8 MiB，一次 `stage` 最多 4 MiB 字节，所以一个大文件分几帧走。批量仍为 256 条。

**6b：真对端。** `serve` 子命令、握手、结果 `Sync`、执行包夹（push → spawn → pull）。验收：杀掉对端后重连，续传不重复应用。

`serve` 打开一个库、监听一个 unix socket、回答请求，并把自己的库挂进 FUSE，好让命令用真实路径。

**6c：远端执行。** `exec` 请求启动命令，输出流成帧回来，出口一帧 `exit`。取消走第二条连接上的 `kill`，所以 exec 流始终是单向的。宿主持有输出文件与尾部窗口，对端只发字节。

落地后的约定：

- 请求带工作区路径，不带本机真实路径。对端用 `mount.Resolver` 解析并惰性挂载。
- 未知 exec id 回 `EEXEC_LOST`：这个 id 属于已消失的进程，不是“从未存在”。
- 输出帧走 JSON（`[]byte` 即 base64）；对象字节仍走原始分段。
- 线格式类型属于 `peer`，与 `vfs` 显式转换。存储结构改名不能变成协议变更。
- `peer.Open` 在构造里握手，所以不存在“未握手的客户端”。
- 只有声明 `Local()` 的后端才拿到本机真实路径。远端命令不解析、不挂载。

落地后多出两条约定：

- 每次 push 结尾发一次 `ping`，断言对端的 `applied` 游标覆盖本次推送。`ping` 让“没有变更可推”的对端也回答，安全门才真的关上。
- push 与 pull 各重试一次，重试前换会话。两个方向都是状态式，重发不会重复写。

**句柄缓存在 6c 落地。** `Handle` 加了 `Closed()`。`Runtime` 按 backend id 缓存一个句柄，一个句柄同时只跑一条命令，传输错误即丢句柄。命令从不重放：对端在空闲期重启时，宿主的下一条命令失败一次，再下一条重连成功。这个代价是刻意的，见 §5.5。

## 重新评估的触发条件

1. 出现跨机器执行体：换 `Transport` 实现为反向拨号。
2. 需要空目录传播：回来改“目录创建不产生变更事件”。
3. 镜像库开始与权威库漂移（例如有人直接改镜像库）：回来讨论镜像是否该只读。
