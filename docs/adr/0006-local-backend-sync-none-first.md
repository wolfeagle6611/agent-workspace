# ADR 0006: 第一阶段只做 `sync: "none"` 的本地后端

Status: accepted（本项目决策，非逆向整理）

## 背景

取法对象的核心是“权威存储 + 同步协议”。但我们的组合是：执行体为同机子进程（Q17），工作区通过 FUSE 以真路径暴露（Q23），FUSE 由持有权威 SQLite 的同一进程服务（Q26 c）。

这个组合下不存在第二份存储。同步协议没有对手方。

## 决策

第一阶段只实现一个声明 `sync: "none"` 的本地后端。`Backend`、`Handle`、`SyncMode`、`Exec` 的形状现在就定死。水位、按路径合并、`(rev, path)` 双坐标游标、对象探测与补传全部推迟到第二个后端出现时。

`rev` 仍然每次写入都铸造，因为 FUSE 写入与 `baseRev` 前置条件要用它。没有消费者不等于不需要。

## 放弃的方案

**先做镜像 + 同步（上游形状）。** 放弃原因：为不存在的对手方写协议。测试只能自己造一个假对端，而假对端会把真问题（乱序、断线、半批）藏起来。

**完全不设计接口。** 放弃原因：加第二个后端时要改 `Workspace` 和所有调用方。接口形状便宜，现在定。

## 后果

- 第一阶段省掉 L2 的全部实现与测试面。
- 冲突保护不经过网络，所以 `baseRev` 前置条件是第一阶段唯一的一致性机制。它必须在这一阶段做完，不能等。
- 唯一需要回头改的行为点是 `Workspace` 的 `push` / `pull`：从空操作变成真实操作。调用方不需要改，因为签名不变。
- 第一阶段**不建水位表**。等第二阶段再加，用一次 schema 迁移带上。提前建空表只会让它腐烂。

## 重新评估的触发条件

出现以下任一情况，回到本 ADR：

1. 需要远端执行（执行体与权威库不在同一台机器）。
2. 出现第二个进程要读同一工作区。
3. FUSE 的同进程服务成为性能或可靠性瓶颈。
