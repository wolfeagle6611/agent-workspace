# ADR 0007: exec 的写入不受 `baseRev` 约束

Status: accepted（本项目决策）

## 背景

`baseRev` 是第一阶段唯一的一致性机制（ADR 0006）。它要求写者声明“我读到的版本”，不匹配就拒绝写入。

但执行体是子进程。它拿到的是一个真路径，然后 `open` / `write` / `close`。它无法携带版本号，也不会在收到冲突后重读再试——它可能是一条 `sed -i`，也可能是一个跑了十分钟的构建。

## 决策

`baseRev` 只约束工作区 API 的写入（`fs.WriteFile`、`fs.Remove`、`fs.Rename` 等）。exec 的写入总是生效，视为不可中断写者。

冲突报告只发生在“写者带前置条件、而目标已被改动”时。exec 改变文件的版本，从而让随后带过期 `baseRev` 的写入失败；反过来，exec 不会因为有人持有旧版本而失败。

## 放弃的方案

**执行期间给被写路径打脏标记，事后报冲突。** 放弃原因：报冲突时命令已经结束，调用方无法回滚，只能人工收拾。错误从“阻止”退化成“噪音”。

**执行期间对整个工作区加写锁。** 放弃原因：命令可能跑十分钟，锁定期间所有 API 写入失败。并发直接归零。

## 后果

必须写进用户文档，不能只留在本 ADR：

- 带 `baseRev` 的写者可能覆盖 exec 期间产出的文件，反之亦然。
- `baseRev` 保护的是“两个 API 写者之间”，不是“API 写者与命令之间”。
- 需要强一致的场景，用“默认 1 个并发执行”（见 `go-mapping.md` §6）加显式交接，不要依赖 `baseRev`。

这条决定一旦有用户依赖，反转代价高：改成 exec 也受约束会让所有长命令变脆。
